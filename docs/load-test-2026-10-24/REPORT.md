# 2026-10-24：4 核 / 4 GiB 混合负载结果

本次测试的结论是：**批改先排队，混合负载随后出现延迟和超时；这几轮都没有 OOM。现有保护能保住进程并自动恢复，但还不能保证高峰读取延迟。** 不建议据此承诺万人同时操作。

基线为 `e30b91b5`，本轮只增加压测夹具和报告，没有修改应用运行逻辑。硬限额经内核文件验证：CPU `400000 100000`（4 核配额）、memory.max `4294967296`（4 GiB）、memory.swap.max `0`。Node 24.19.0，x64，宿主 CPU 型号 Xeon Platinum 8573C。容器主 API 堆上限 1024 MiB，默认上传并发 2、后台批改并发 1，同校批改待处理上限 25。模拟模型耗时 2 秒。每张上传 JPEG 约 1.42 MiB。

合成数据为 100 个教师、10000 个学生、100 份作业、10000 份初始提交。混合比例为读取 70%、登录 5%、上传 10%、批改入队 10%、资料写入 5%。详细口径、命令、接口分布和限制见 [LOAD_TESTING.md](../../LOAD_TESTING.md)。一万个账户是数据规模，**不等于一万个同时活跃连接**。

## 读取什么时候开始退化

B 轮使用不同用户来源 IP，每级持续 20 秒。p95/p99 只统计成功读完整响应的读取；超时单列，避免成功样本掩盖失败。

| 目标总请求/秒 | 成功读取 p95 / p99 | 读取超时 / 实际发出的读取 | 客户端未发出的总请求 | 阶段末状态 |
| --- | --- | --- | --- | --- |
| 20 | 7 / 22 ms | 0 / 280 | 0 | 正常 |
| 100 | 3 / 5 ms | 0 / 1400 | 0 | 正常 |
| 150 | 13 / 68 ms | 0 / 2100 | 0 | 正常 |
| 200 | 4398 / 4708 ms | 227 / 2240 | 807 | 严重降载 |
| 300 | 186 / 1057 ms | 0 / 4200 | 0 | 严重降载，仍在恢复等待 |
| 600 | 99 / 439 ms | 0 / 8400 | 0 | 降载 |
| 1200 | 4273 / 4814 ms | 904 / 5173 | 16619 | 降载 |

客户端总在途上限为 512，发起后目标超时为 5 秒。1200 是施压目标，不能当成服务完成 1200 次请求/秒。300/600 阶段的读取变快，是在前一阶段触发保护、上传大量被拒绝的条件下得到的；不能解释成“600 比 200 更安全”。到了较后阶段，同校每日 500 个上传会话的配额也已经消耗完，进一步减少了实际上传处理量。

用新数据库、不跑慢上传和锁故障，C 轮重复 100/200/300：读取 p95 为 5/781/26 ms，均无读取超时；200 阶段已进入降载，300 延续该状态。200 次/秒的两轮结果明显波动，说明它是需要留余量的区间，**并不是确定、可移植的容量断崖**。没有证据把波动单独归因于 CPU、磁盘或某一条 SQL；同步数据库工作和事件循环停顿是后续需要采样分析的对象。

A 轮先探索到 5000 次/秒，但上传共用一个 IP，受到 600 次/分钟限制，仅作过载筛查。300 阶段读取成功 p95 为 3039 ms；1200 阶段有 359/10148 个读取超时；5000 阶段客户端跳过 83655 个请求、1909/11415 个实际读取超时。因此没有测出“5000 RPS 容量”。

## 批改为什么很早就排队

20 次总请求/秒包含约 2 次批改入队/秒。单个后台执行槽等待 2 秒模型响应，再加调度与处理，实测常态完成约 0.4 次/秒。队列约十几秒内接近同校 25 个上限，之后返回 429，读取仍快。队满时大致需要一分钟消化；受控暂停期间观察到最老待处理任务年龄约 117 秒。

这是业务处理速率差导致的排队，不需要先耗尽 CPU 或内存。模型变为 10 秒响应时，一个执行槽的吞吐还会下降到约 0.1 次/秒，不能套用本次 2 秒模型的完成速度。当前队列不会无限接收万人同时提交；达到上限后的客户端需要稍后重试。

## 内存、慢上传和写锁

- B 轮 16 个不同用户同时慢上传，实际接收 2 个（约 4.62 秒完成），其余 14 个返回 429。与此同时 999 次背景读取全部成功，p95 4 ms，最大 61 ms。验证的是上传槽和流背压，不是互联网慢连接的全部行为。
- A 轮额外用独立助手在同一 cgroup 分配真实匿名内存。可用预算约 375 MiB 时进入 limited；约 170 MiB 时进入 critical。critical 阶段 100 个新增上传全部被拒绝（67 个 HTTP 503，33 个连接提前关闭），后台不再领取新任务。两个内存阶段分别 699 次读取均成功，p95 都约 3 ms。
- 撤去内存助手后，75 秒恢复窗口末回到 normal，后台成功任务数从 82 增至 99；该窗口读取全部成功，p95 24 ms、最大 422 ms。没有人工重启。
- B 轮另一个进程持有真实 SQLite 写锁 3 秒，同时维持每秒 100 次混合请求。699 次读取都成功，但 p95 升至 2381 ms，66 次超过 2 秒；部分登录/上传返回 400（当前 SQLite 错误映射），而非合适的繁忙提示。锁解除后读取 p95 恢复到 7 ms。**单次 busy_timeout=250 ms 不能防止连续多个写请求累计阻塞事件循环。**

B 轮 API RSS 峰值约 302 MiB，容器累计内存峰值约 1201 MiB（包含文件缓存、转发进程和内核计费）；C 轮约 260/917 MiB。A 轮加入内存助手后容器峰值约 3941 MiB，API 自身 RSS 最高约 336 MiB。三个容器的 `memory.events` 均无 OOM/oom_kill，停止前进程都还在运行，无重启。

没有获得“多少并发必定 OOM”的数值。当前保护在本次输入规模下先限制或拒绝工作；更大的无分页列表、更大解析任务、泄漏、其他同机服务仍可能改变内存曲线。强行让助手超过硬限额只能证明内核会杀进程，不能测出应用的用户容量，所以没有这样做。

## 部署含义

建议以总动态请求约 50～100 次/秒作为当前部署的保守限流起点，结合真实延迟和拒绝率调整；这不是已经验证的长期服务等级。超额重任务应在入口尽早拒绝或有界排队，客户端退避重试。当前动态策略主要保护重任务，普通读取与同步写入仍共享一个事件循环；下一步优先评估全局有界准入、列表分页、热点统计计算及数据库写入隔离，而不是盲目提高上传/模型并发。

4 GiB 是整个测试容器的硬上限，宿主操作系统、Nginx、TLS 和压测客户端在外部。当前部署示例给主服务的 MemoryMax 是 2.5 GiB，以便在 4 GiB 整机上留出系统空间；本次容器限额不能视为已经复现了那台整机。客户端与容器还共享外层执行器的 4 核 CPU 配额。没有验证公网 Files API、PDF/Word 解析、备份并发、真实换页、慢盘/磁盘故障，也没有进行数小时稳定性测试。
